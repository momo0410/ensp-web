### 2.2 不具备（本轮需求暴露的空白）

- **抓包能力**：全仓不存在。检索 `capture` 仅命中 ping 输出里的 `packet(s) transmitted` 与 `subprocess.capture_output`。
- **单台设备启停**：`tools/ensp_control.cpp` 仅实现 4 条指令（367-379 行）：`start_all` / `stop_all` / `status` / `live_topo`。

- **批量变量化下发**：有默认值与冲突检测，但无「模板 + 变量序列 → 一次下发」的执行器。

## 三、逐条评估

### 1. 项目 ↔ eNSP 启动联动（可开关）

**正向（项目启动 → 拉起 eNSP）**

- **现状**：`ensure_ensp_injected(launch_if_missing=True)` 已能拉起 `eNSP_Client.exe`、等待主视图、注入 DLL。但仅在「添加设备」「应用拓扑」时被调用；`main.py: startup_event` 只做单实例锁、缓存回灌、启动采集线程，**完全不触碰 eNSP**。
- **方案**：在 `app_settings.json` 增加开关项（如 `auto_launch_ensp: true`）；`startup_event` 中若开关打开，起后台线程调用 `ensure_ensp_injected()`，避免阻塞启动。
- **工作量**：小。**风险**：低。注意注入需管理员权限，失败应降级为非阻塞告警。

**反向（eNSP 启动 → 拉起项目）**

- **卡点**：eNSP 是闭源 GUI 程序，**没有任何插件或回调机制**，真正的事件级 hook 无法实现。
- **可行替代**：
  1. **启动器包装**：桌面快捷方式指向自研 launcher，先起后端再起 eNSP（最简单、最可靠）；
  2. **常驻看护进程**：轮询 `eNSP_Client.exe` 进程是否存在，存在则拉起后端（需配合计划任务或登录自启）。
- **工作量**：中。**风险**：中（涉及 Windows 自启机制，机房环境需逐台配置）。

### 2. 拓扑双向同步

**正向（项目建/开拓扑 → eNSP 立即打开）**

- **现状**：`open_topology_in_ensp()` 已具备（RPC 加载 `.topo`），`POST /api/ensp/topo/apply` 已在用。
- **缺口（明确）**：`routes_devices.py: topology_activate / topology_create` **均未调用它**。当前切换或新建拓扑时，eNSP 完全不知情，两侧会脱节。
- **方案**：在 `ws.set_active()` / `ws.create_topology()` 成功后追加 `open_topology_in_ensp(topo_path)`，并复用 `_verify_open_matches()` 校验打开结果与预期设备一致。
- **工作量**：小。**风险**：低。

**反向（eNSP 打开拓扑 → 项目感知并可操作）**

- **现状（感知已有）**：`GET /api/ensp/live` + `read_ensp_topology()` + `compare_with_active_topology()` 已能判断 `in_sync / drifted`，前端轮询可见「用户在 eNSP 里做了什么」。
- **缺口**：**只能看、不能接管**。缺少把 eNSP 侧拓扑反向导入为项目拓扑的动作。
- **方案**：新增「从 eNSP 导入」动作——`live_topo` → 解析设备清单 → 复用 `allocate_console_port()` 分配端口 → 生成 `devices.json` + `links.json` → `ws.set_active()`。
- **工作量**：中。**风险**：中（`live_topo` 字段结构与型号识别需实测确认）。

### 3. 设备启停

- **全部启停**：✅ 现成，`POST /api/ensp/start-all` `/stop-all`，前端 `DevicesView.tsx` 已有按钮。
- **单台启停**：❌ **DLL 不支持**。
- **卡点**：`tools/ensp_control.cpp` 仅 4 条指令，靠硬编码偏移（`ENSP_G_PMAINFRAME = 0x005F4E40`）调用 eNSP 内部函数。
- **可行路径**：
  1. **扩展 DLL**：逆向定位单设备启动的调用点，新增 `start_dev:<name>` / `stop_dev:<name>` 指令，**需重新编译 32 位 DLL**，且必须与 eNSP 版本严格匹配；
  2. **UI 自动化**：DLL 已注入进程内，可 `PostMessage` 模拟设备节点右键菜单点击（避开逆向，但仍依赖界面布局）。
- **工作量**：大。**风险**：**中高**——建议先做技术验证（spike）再决定投入。

### 4. 一键抓包 + AI 分析

- **现状**：❌ 完全不存在。
- **三条技术路径**：

| 路径 | 依赖 | 评价 |
|------|------|------|
| 逻辑路径追踪（推荐优先） | 零新依赖 | 用 `display arp/mac-address/ip routing-table/ospf peer` + 逐跳 `ping -a` 推断转发路径与断点，**立刻可做** |
| Wireshark 联动 | 装 Wireshark + GUI 操作 | 可通过 DLL 扩展或 UI 自动化触发链路抓包 |
| npcap 抓虚拟网卡 | 装 npcap 驱动 + `scapy`/`pyshark` | 能抓到真包，但机房机器装内核驱动有门槛 |

- **建议**：先落地**逻辑路径追踪**作为「数据包走向」的等价能力（零依赖、教学价值高），真抓包列为第二阶段，先做 npcap 可行性验证。

### 5. 协议与指令识别

- **现状**：✅ 项目最成熟部分。三层证据（镜像能力矩阵 / `?` 命令树 / display 探测），判定优先级 `?` 树 > 矩阵 > 探测，每项带 `evidence` 字段；31 项协议、26 条命令目录、`?` 探测引导接口齐备。
- **可优化**：命令目录仅 26 条未覆盖全部 VRP 指令；`?` 树采集有硬性时间预算，可能采不全。
- **结论**：本条已基本满足，后续按使用反馈扩充目录覆盖度即可。

### 6. 指令下拉补全

- **现状**：❌ 无。`help_tree.py` 可抓 `?` 树，但前端是静态卡片目录，不随输入上下文变化。
- **缺口**：缺「`?` 树 → 前缀树」的组织层，以及带补全的 CLI 输入框。
- **方案**：
  1. 后端新增上下文补全服务：`display` → `[version, cu, ip interface brief, ...]`，按设备缓存（复用现有 30 分钟 TTL 缓存机制）；
  2. 前端在 `CatalogPanel` 之外新增 CLI 输入框，输入即下拉候选。
- **工作量**：中。**风险**：低。**ROI 最高**——数据基础现成，只差组织与呈现。

### 7. AI 配置设备 / 搭建拓扑

- **现状**：⚠️ AI 当前**只建议不执行**（安全红线设计），命令可「发送到工作台」，下发必须走备份 → 预览 → 确认 → 验证链路。
- **方案（必须 schema 化）**：
  1. AI 输出受约束的 **JSON plan**（不得是自由文本），后端校验后再执行；
  2. 配置：plan → 逐条预览 diff → 人工确认 → 复用现有下发链路；
  3. 拓扑：AI 输出拓扑 JSON → `build_topo_spec_from_devices()` → 生成 `.topo` → eNSP 打开。
- **关键约束**：**绝不允许 AI 自由文本直接灌入设备**。确认闸门不可省略。
- **工作量**：中。**风险**：中（AI 输出稳定性、错误配置的下发风险）。

### 8. 批量变量化下发

- **现状**：⚠️ 有 `smart-defaults`（批量默认值）、`check-batch-conflicts`（冲突检测）、`clone/deploy`（复制到多设备），但**没有变量序列下发**。
- **缺口**：无法表达「同一模板，5 台设备 IP 依次为 192.168.1.1~5，一次下发」。
- **方案**：新增批量执行器——
  1. 模板 + 变量序列定义（起止 IP、步长、编号递增）；
  2. 按设备展开变量 → 复用 `free_config_renderer` 的 `{{变量}}` 渲染；
  3. 经 Console 通道**并行下发**（并发能力已具备）；
  4. 下发前自动备份，失败逐台回滚并报告。
- **工作量**：中。**风险**：低。**与你举的 OSPF 5 台场景直接对口**。

## 六、风险登记册

| 风险 | 影响 | 应对 |
|------|------|------|
| eNSP 版本与 DLL 硬编码偏移不匹配 | 注入失败，全部联动功能失效 | DLL 需随 eNSP 版本维护；失败降级为手动模式并明确提示 |
| 单台启停需改 32 位 DLL | 逆向工作量大、可能失败 | 先做 spike；准备 UI 自动化兜底方案 |
| npcap 驱动在机房批量部署困难 | 抓包功能无法推广 | 优先落地零依赖的逻辑路径追踪 |
| AI 输出不稳定导致错误配置下发 | 设备配置被改坏 | schema 约束 + 预览 diff + 人工确认闸门 + 下发前自动备份 |
| eNSP 无回调机制 | 反向联动只能轮询 | 采用启动器包装 / 看护进程，接受"非事件级"实现 |
