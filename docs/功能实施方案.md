# eNSP Web 功能实施方案

> 本文档为「功能规划与可行性评估.md」的落地版：把待建功能拆成可独立实施、可独立验证的步骤。
> **验证约定**：涉及 eNSP 的改动一律走「启动服务 → 调 HTTP API → 观察 eNSP 侧真实反应」，
> 详见 `AGENTS.md` 第四节。以下每步末尾均给出验证清单。

---

## 〇、总览：实施顺序与依赖

| 步骤 | 功能 | 依赖 | 风险 | 建议批次 |
|------|------|------|------|----------|
| S1 | 命令上下文补全（`?` 树 → 前缀树 + 前端补全） | 无（数据现成） | 低 | 第一批 |
| S2 | 拓扑双向联动（项目→eNSP 打开同步；eNSP→项目感知/导入） | 无 | 中 | 第一批 |
| S3 | 批量变量化下发引擎（IP 序列递增同配） | 无 | 低 | 第一批 |
| S4 | AI 结构化 plan（配置 / 拓扑 schema 化） | S1/S3 的通道 | 中 | 第二批 |
| S5 | 逻辑路径追踪器（抓包轻量替代） | 无 | 中 | 第二批 |
| S6 | 单台设备启停（扩展 DLL / UI 自动化） | spike | 中高 | 第三批（先 spike） |
| S7 | 真抓包（npcap） | spike | 中高 | 第三批（先 spike） |

**第一批（S1/S2/S3）可并行开发、互不阻塞**，且都是「数据基础现成、只差组织与呈现」，故先做。

## 一、S1 命令上下文补全

### 1.1 目标

在 CLI 输入框内，随输入前缀给出候选命令（如输入 `display` 下拉出
`version` / `current-configuration` / `ip interface brief` …），选中即补全。
支持按设备（用其实测 `?` 树）、按视图（系统视图 / 接口视图 / 用户视图）区分候选。

### 1.2 现状与可复用资产

| 资产 | 位置 | 说明 |
|------|------|------|
| `?` 树采集 | `services/help_tree.py` `collect_views_console` / `collect_views_over_connection` | 返回 `views = {"display": set, "system": set, "interface": set}`，**单层关键字、无描述** |
| 关键字解析 | `services/help_tree.py` `parse_help_keywords` | 丢弃描述，只留 token |
| 探测缓存 | `services/command_probe.py` `get_cached_probe` / `set_cached_probe` | 进程内 `_probe_cache`，TTL 1800s，含 `views` + `keywords` |
| 异步范式 | `routes_config.py` `probe_catalog` | 缓存命中同步返回；未命中 BackgroundTasks + job_id + 前端 800ms 轮询 |
| 前端输入框 | `ConfigDeployView.tsx:378`（单设备原始命令）、`WorkbenchView.tsx:395`（批量模板） | 均为等宽 `Textarea`，无补全 |
| 前端控件 | `@mantine/core` | 已依赖 Mantine 9，可用 `Autocomplete` / 自绘下拉 |

### 1.3 关键约束

- `?` 树只有**单层关键字、无描述、无二级子命令**。多级补全（`ip` → `route-static`）
  需要扩展采集（对前缀再发 `?`），属增量演进，**S1 只做"当前视图单层关键字 + 目录模板命令"两层候选**。
- `?` 必须单独成行，**绝不发 `ospf 1 ?`**（会真执行）；补全采集必须遵守（复用既有采集器即安全）。
- 补全候选要**提示来源**（设备实测 `?` / 内置命令目录），避免误信。

### 1.4 实施设计

**后端**——新增 `services/command_complete.py`：

```
complete_commands(target, prefix, view=None, device_type=None) -> list[candidate]
candidate = {"text": str, "desc": str, "source": "?" | "catalog", "view": str}
```

- 数据源 1：`get_cached_probe(cache_key(target))` 的 `views`（设备实测）。
  命中 → 直接过滤 `prefix` 前缀；未命中 → 返回**目录候选**并标记 `source="catalog"`，同时可选触发后台 `?` 探测。
- 数据源 2：`COMMAND_CATALOG` 的 `trigger` + `command_template` 首 token（内置标准写法）。
- 前缀匹配：大小写不敏感 `candidate.text.lower().startswith(prefix.lower())`。
- 视图推断：无显式 `view` 时按补全上下文（用户视图/系统视图）取对应层；目录候选归"系统视图"。

新增路由（`routes_config.py`，复用探测缓存，不新增采集）：

```
GET  /api/command-complete?ip=<dev_ip>&prefix=<p>&view=<v>
     → 命中缓存 200 {success, candidates, from_cache:true}
     → 未命中 200 {success, candidates:<catalog候选>, from_cache:false, hint:"缓存未命中，候选为内置目录"}
POST /api/command-complete/probe   {target, force}   # 复用 /api/command-catalog/probe 的探测机制（可复用同一 job 存储）
```

> 实现上，若不想新增 job 存储，可直接复用 `/api/command-catalog/probe` 与
> `/api/command-catalog/probe/{job_id}` —— 补全只读其缓存即可。

**前端**：

- 新增 `frontend/src/components/CommandInput.tsx`：基于 Mantine `Autocomplete` 或自绘
  下拉，封装「等宽样式 + 防抖(300ms) + 调 `/api/command-complete` + 键盘上下选 + 回车补全」。
- 挂载点：
  1. `ConfigDeployView.tsx` 的 rawCommands：单行补全（改为逐行输入 + 当前行补全）。
  2. `WorkbenchView.tsx` 的 commands：复用已有 600ms 防抖逻辑，补全**不得破坏 `{{变量}}` 提取**（补全仅填充命令 token，变量行原样）。
- 新建补全控件单选设备：从 `store` 的 `devices` 取，请求带 `ip`。

### 1.5 涉及文件

- 新增：`services/command_complete.py`、`frontend/src/components/CommandInput.tsx`
- 修改：`routes_config.py`（补全路由）、`frontend/src/views/ConfigDeployView.tsx`、
  `frontend/src/views/WorkbenchView.tsx`、`frontend/src/types.ts`（补全候选类型）
- 测试：`tests/test_command_complete.py`（纯函数：前缀过滤、来源标注、视图归并）

### 1.6 验证清单

- [ ] 离线：`python -m pytest tests/test_command_complete.py` 全绿。
- [ ] 端到端（真机）：启动 `python main.py --web`，选一台在线设备，
  `GET /api/command-complete?ip=...&prefix=disp` 返回含 `display` 候选；
  在页面输入 `disp` 下拉可见 `display`，选中后正确补全。
- [ ] 首次未命中缓存时返回目录候选且 `from_cache=false`；触发探测后再查命中设备实测候选。

## 二、S2 拓扑双向联动

### 2.1 目标

- **正向（项目→eNSP）**：项目「新建/切换/应用」拓扑时，eNSP 立即打开对应 `.topo`（含开关）。
- **反向（eNSP→项目）**：eNSP 里打开/切换了拓扑，项目能感知，并提供「从 eNSP 导入为项目拓扑」动作，
  导入后可正常采集/下发。

### 2.2 现状与可复用资产

| 资产 | 位置 | 说明 |
|------|------|------|
| 拉起+注入 | `domain/ensp_runtime.py` `ensure_ensp_injected` | 已能拉起 eNSP 并注入 DLL（`_auto_launch_ensp` 已有开关 `auto_launch_ensp`） |
| 命令行打开拓扑 | `open_topology_in_ensp` | 用 `eNSP_Client.exe <path>`，比对设备名集合确认 |
| 只读观测 | `read_ensp_topology` / `probe_ensp_live` / `compare_with_active_topology` | 返回 `live_devices`（name/model/power_state）、`in_sync` 状态 |
| 同步打开闸门 | `routes_devices.py` `_open_in_ensp_if_possible` + 设置 `auto_sync_ensp_topo`（默认 True） | 已接入 activate/create |
| 前端轮询 | `DevicesView.tsx` `setInterval(...,3000)` → `GET /api/ensp/live` | 已有 3s 轮询 |
| 工作区 | `domain/workspace.py` `set_active` / `save_topology` / `create_topology` | 反向导入落库用 |

### 2.3 关键缺口

1. **正向**：`_open_in_ensp_if_possible` 已在 `topology_activate`/`topology_create` 调用，
   但 `ensp_apply_topo` 走的是全量 `sync_and_start_ensp_topo`（会重新生成 + 开机），
   且 `topology_create` 新建空拓扑无 `.topo` 时不会打开——行为需统一与补全。
2. **反向**：
   - 只读观测**已有**，但 `in_sync` 结果前端**未消费**（`DevicesView` 的 `EnspLive` 未用 `in_sync`）。
   - **没有"感知到 eNSP 换拓扑 → 自动/手动激活项目对应拓扑"** 的动作。
   - **没有"从 eNSP 导入为项目拓扑"**：`read_ensp_topology` 只拿到 `name/model/power_state`，
     **拿不到接口/连线**（`links` 只是画布线数）→ 反向还原 `links.json` 不可行。
3. `active_topology()` 有写盘副作用（`.current` 缺失即写），高频探测下需注意。

### 2.4 实施设计

**正向（补齐与统一）**：

- 抽一个统一入口 `_sync_active_topology_to_ensp(auto_start=False)`，在 activate/create/apply 后调用：
  - 有 `.topo` → `open_topology_in_ensp`；无 → 记录"待生成"。
  - 受设置 `auto_sync_ensp_topo` 控制（已存在）。
- `topology_create`：新建后不强行打开空拓扑，但返回 `ensp` 字段说明原因（已有此结构）。

**反向（感知 + 导入）**：

1. **感知增强**：`GET /api/ensp/live` 已在返回 `in_sync`；
   前端 `DevicesView` 消费 `in_sync`，当 `status=="drifted"` 时给出醒目提示
   （"eNSP 里是另一套拓扑，是否切换/导入？"）。
2. **反向激活**：新增
   ```
   POST /api/ensp/attach-active   { mode: "match_by_devices" | "import_as" , name?: str }
   ```
   - `match_by_devices`：读 `read_ensp_topology()` 的设备名集合，在 `list_topologies()` 里
     找**设备名集合一致**的拓扑，`set_active` 之（不重建，直接对齐）。
   - `import_as`：把 eNSP 当前设备清单**导入为新的项目拓扑**——`name/model/power_state`
     → 设备表条目（分配 `console_port`，复用 `allocate_console_port`），
     `links` **置空并标注"连线需在 eNSP 侧确认或手动补"**（因无法反向还原）。
3. **连线限制要在 UI 明示**：导入的设备可采集/下发，但连线需手动补——避免误导。

> **理由**：eNSP 内存只暴露设备（name/model/power），不暴露端口级连线，
> 强行"反推拓扑"违背项目「权威拓扑源是 .topo」的设计。反向只做"对齐/导入设备清单"，不臆造连线。

### 2.5 涉及文件

- 修改：`routes_devices.py`（`_sync_active_topology_to_ensp`、`ensp_attach_active`）、
  `domain/ensp_runtime.py`（如需暴露 `read_ensp_topology` 的稳定字段不变）、
  `frontend/src/views/DevicesView.tsx`（消费 `in_sync` + 导入/切换按钮）、
  `frontend/src/store.tsx`（`attachActive` 动作）、`frontend/src/types.ts`
- 测试：`tests/test_ensp_attach.py`（用 monkeypatch 假 `read_ensp_topology`，验证匹配与导入逻辑，纯离线）

### 2.6 验证清单

- [ ] 端到端正向：启动 `python main.py --web`，`POST /api/topology/library/activate {name}`，
  观察 eNSP **真的切到该拓扑**（比对 `GET /api/ensp/live` 的 `live_devices`）。
- [ ] 端到端反向：在 eNSP 里手动打开另一套拓扑 → `GET /api/ensp/live` 显示 `in_sync.status=="drifted"`；
  调 `POST /api/ensp/attach-active {mode:"match_by_devices"}` → `active` 变为匹配拓扑。
- [ ] 端到端导入：`POST /api/ensp/attach-active {mode:"import_as", name:"imported"}` →
  新拓扑 devices 数 = eNSP 设备数；`GET /api/devices` 可见；随后采集能连上 Console。

## 三、S3 批量变量化下发引擎

### 3.1 目标

表达「同一模板 + 变量序列 → 一次下发 N 台」，例如 OSPF 区域 0 中 5 台设备
IP 依次 `192.168.1.1` ~ `192.168.1.5`，一次完成相同配置。

### 3.2 现状与缺口

- **已有**：`{{变量}}` 模板渲染（`free_config_renderer`）、`smart-defaults`（批量默认值）、
  `check-batch-conflicts`（冲突检测）、`free-deploy`（批量逐台执行）、`WorkbenchView`（批量工作台）。
- **缺口**：不能表达「变量按序号递增/按网段序列展开」。用户现在要手填 5 行变量表。

### 3.3 实施设计

**后端**——新增 `services/batch_variables.py`：

```
expand_variable_series(spec, devices) -> dict[ip -> {var: value}]
spec = {
  "base": {"router_id": "192.168.1.{i}", "ospf_network": "10.0.{i}.0"},
  "start": 1, "step": 1, "width": 0,
  "per_device_overrides": {"192.168.1.3": {"router_id": "..."}},   # 可选
}
```

- 支持占位符 `{i}`（序号）、`{i:02d}`（补零）、`{ip_last}`（设备末段）等；用 Python `str.format` 语义。
- 序号基数/步长/起始可配；`per_device_overrides` 允许个别设备偏离序列。
- 输出直接喂给现有 `free_config_renderer` 渲染 → 现有 `free-deploy` 批量执行，
  **不新增下发路径**（复用备份→预览→确认→验证链路）。

新增路由：

```
POST /api/config/preview-series   {commands, target_devices, series, save_config}
     → 返回逐台渲染结果 + 冲突检测（复用 free_config_preview 的冲突逻辑）
POST /api/config/deploy-series    {同上}
     → 复用 free_config_deploy 逐台下发
```

> 更省事的做法：给现有 `free_config_preview`/`free_config_deploy` 的请求模型
> **增加可选 `series` 字段**，由后端展开变量后再走原逻辑。**推荐此方案**（改动最小）。

**前端**——`WorkbenchView.tsx` 变量区新增「序列模式」：

- 变量表格（现有）与「序列生成」二选一：填 base 模板 + 起止/步长，实时预览生成的逐台变量。
- 冲突检测仍走现有 Banner（`hasBlockingErrors` 阻止下发）。

### 3.4 涉及文件

- 新增：`services/batch_variables.py`
- 修改：`routes_config.py`（`free_config_preview`/`deploy` 支持 `series` 或新增 series 路由）、
  `app/models.py`（请求模型加 `series`）、`frontend/src/views/WorkbenchView.tsx`、
  `frontend/src/types.ts`
- 测试：`tests/test_batch_variables.py`（`expand_variable_series` 序列展开、补零、override，纯离线）

### 3.5 验证清单

- [ ] 离线：`python -m pytest tests/test_batch_variables.py` 全绿。
- [ ] 端到端：选 5 台在线设备，`series.base={"router_id":"192.168.1.{i}"}` start=1，
  预览显示 5 台分别 `192.168.1.1..5`；确认下发后逐台读回 `display ospf` 验证
  router-id **在设备上真的各自不同**（证明不是同一条灌了 5 遍）。
- [ ] 冲突检测：故意让两台序列重叠 → 预览被 Banner 拦截。

## 四、S4 AI 结构化 plan

### 4.1 目标

AI 从"只出文本建议"升级为"输出受约束的 JSON plan"，经校验后进入现有预览/确认/下发链路。
覆盖两类 plan：**配置 plan**、**拓扑 plan**。

### 4.2 现状与红线

- AI 现状：`services/ai_assistant.py`（`chat_once`/`chat_stream`/`build_messages`），
  提示词硬性"只能建议不能执行"。命令只能经 `AiMarkdown` → 工作台文本框。
- **红线（不可破）**：AI 输出**绝不直接下发**，必须走 备份→预览→确认→验证。
  危险命令拦截、确认闸门不可省略（`AGENTS.md` 第六节）。

### 4.3 实施设计

- 新增任务类型 `task="plan"`，提示词要求 AI **只输出 JSON**（无自然语言、无 ``` 包裹），schema：
  ```
  {"kind":"config","targets":["<ip>"],"commands":["..."],"explain":"...","risks":["..."]}
  {"kind":"topology","devices":[{"name","model","cx","cy"}],"links":[{"a":{"device","interface"},"b":{...}}]}
  ```
- 后端 `POST /api/ai/plan`：调 AI → 提取并 `json.loads` → **schema 校验**（字段白名单、型号白名单、
  IP/网段格式、命令不含危险关键字）→ 返回 plan + 校验结果；**不执行**。
- 前端：plan 渲染为"配置预览面板"，一键"送入工作台/预览"（复用现有链路），
  拓扑 plan 一键"生成并打开拓扑"（复用 `sync_and_start_ensp_topo`，同样需确认）。
- 复用：`services/free_config_renderer` 的危险命令检查；`tools/gen_topology.py` 的型号校验。

### 4.4 涉及文件

- 修改：`services/ai_assistant.py`（plan 提示词 + JSON 提取）、`routes_ai.py`（`/api/ai/plan`）、
  `frontend/src/components/AIDrawer.tsx` / `AiMarkdown.tsx`（plan 卡片）、`frontend/src/types.ts`
- 测试：`tests/test_ai_plan.py`（JSON 提取、schema 校验、危险命令拒绝，纯离线）

### 4.5 验证清单

- [ ] 离线：schema 校验、危险命令（如 `reset saved-configuration`）被拒。
- [ ] 端到端：`POST /api/ai/plan` 返回合法 plan → 前端"预览"显示命令 → 确认后**设备真的收到并执行**；
  拓扑 plan → `POST /api/ensp/topo/apply` → eNSP 真的加载。

## 五、S5 逻辑路径追踪器

### 5.1 目标

给定源/目的 IP，自动采集 `display arp / ip routing-table / ospf peer / mac-address`，
推断转发路径并逐跳 `ping -a` 验证，输出路径图 + 断点定位，可交 AI 分析。
**零新依赖**（纯解析 + 现有 Console 采集），作为真抓包的轻量替代。

### 5.2 实施设计

- 新增 `services/path_trace.py`：
  - 输入：源设备 + 目的 IP；用 `display ip routing-table <dst>` 找下一跳 →
    查 `display arp | include <nh>` 找下一跳 MAC/接口 → 顺藤找到直连邻居设备 →
    递归至目的设备。每跳用现有 `device-ping`（`services/live_check.py`）验证。
  - 输出：`{"hops":[{device, in_if, out_if, next_hop}...], "reachable": bool, "break_at": str|None, "evidence": {...}}`
- 路由：`POST /api/path-trace {source_ip, dest_ip}` → 复用采集缓存（少连接）。
- 前端：设备详情新增"路径追踪"面板，路径图 + 断点高亮；结果可"交给 AI 分析"
  （复用 AI 上下文注入）。

### 5.3 涉及文件

- 新增：`services/path_trace.py`、前端路径追踪组件
- 修改：`routes_devices.py` 或新 `routes_net.py`、`app/models.py`、`frontend` 视图
- 测试：`tests/test_path_trace.py`（用样例 display 输出验证逐跳推断，纯离线）
